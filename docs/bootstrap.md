## 2. Talos VM with OpenTofu

```bash
cd tofu/envs/proxmox
tofu init
tofu plan
tofu apply
```

`terraform.tfvars` is committed and holds the VM inventory. The single-node
layout provisions exactly one VM, which runs the control plane and all
workloads.

Expected VM:

| Name | Role | vCPU | RAM | Disk |
|---|---|---|---|---|
| `talos-cp-1` | control plane + workloads | 6 | 14 GB | 100 GB |

On a fresh state, `tofu plan` shows one create. If it shows the retired
three-node cluster, the local state still belongs to the old host. Archive it
first:

```bash
cd tofu/envs/proxmox
mkdir -p state-archive
mv terraform.tfstate terraform.tfstate.backup state-archive/ 2>/dev/null || true
```

The VM boots the Talos ISO. OpenTofu only creates the shell; Talos configuration
is applied with `talosctl`.

## 3. Talos configuration

From the repository root:

```bash
make secrets
```

Defaults: cluster `home`, control-plane endpoint `https://192.168.178.239:6443`.
Override with `CLUSTER_NAME` or `CP_IP` if needed. No worker configs are
generated by default; use
`WORKERS="talos-worker-1 talos-worker-2" make secrets` only when you add those
nodes back.

This creates:

```text
talos/secrets/secrets.yaml        # gitignored; back this up
talos/generated/talos-cp-1.yaml   # machine config
talos/generated/talosconfig       # client credentials
```

Talos 1.14 emits a multi-document machine config. Fields that moved into their own
documents (`HostnameConfig`, `ResolverConfig`, `UnattendedInstallConfig`,
`KubeNodeConfig`) must be patched in those documents; duplicating them in the
legacy document is rejected at apply time. The specific conflicts and their
workarounds are commented in `talos/patches/`.

Back up `talos/secrets/secrets.yaml` to BSM and the offline recovery kit. Never commit it.

## 4. Bootstrap the cluster

OpenTofu only creates the VM shell; the `ip` value in `terraform.tfvars` is
documentation only. On first boot the Talos ISO runs in **maintenance mode** and
uses **DHCP**, so the VM answers on a lease, not on its final static address.
Find that lease, then pass it:

```bash
make bootstrap MAINTENANCE_IP=<DHCP_LEASE>   # e.g. 192.168.178.90
```

`MAINTENANCE_IP` is required; the Makefile refuses to run without it because the
VM is still on DHCP. After `apply-config` installs Talos to disk and reboots,
the node comes back on the static `.239` address.

The script:

1. applies the control-plane config (installs to `/dev/sda`, then reboots)
2. waits for the node on `CP_IP`
3. retries the etcd bootstrap until etcd is ready (up to 5 minutes)
4. writes kubeconfig to `$KUBECONFIG` (default `~/.kube/config`) and selects
   the context `home`
5. waits for `kubectl get nodes`

To write or refresh only the kubeconfig, without re-running the bootstrap:

```bash
make kubeconfig
# or a different file:
KUBECONFIG=/path/to/config make kubeconfig
```

Verify:

```bash
kubectl get nodes -o wide
```

### Workers (optional, later)

The single-node layout has no workers. If you add the retired host's VMs back:

1. Add matching entries to `vms` in `terraform.tfvars` and apply.
2. Generate their configs with
   `WORKERS="talos-worker-1 talos-worker-2" make secrets`.
3. Each worker starts in maintenance mode on DHCP. Pass both leases:

```bash
export WORKER1_MAINTENANCE_IP=<lease>
export WORKER2_MAINTENANCE_IP=<lease>
make workers
```

The script applies each worker config, waits for its static address, and waits for
the node to become `Ready`. Do not add a second control plane to this host; see
the quorum note in the [README](../README.md).

## 6. Storage

The QNAP is configured; [`proxmox-host.md`](proxmox-host.md) §7 records the
exports and the backup jobs.

| Share | Export | Allowed client |
|---|---|---|
| `k8s` | `192.168.178.254:/k8s` | `192.168.178.239` |
| `k8s-backups` | `192.168.178.254:/k8s-backups` | `192.168.178.249` |

Both use NFSv4.1 with no root squash.

Remaining cluster-side work:

1. Install the `siderolabs/nfs-utils` system extension. Build an Image Factory
   schematic, upgrade the node with the resulting installer image, then record
   the schematic ID in `tofu/envs/proxmox/terraform.tfvars` and in
   [`proxmox-host.md`](proxmox-host.md) §4.
2. Deploy `local-path-provisioner` and keep `local-path` the default
   StorageClass.
3. Deploy `csi-driver-nfs` with an `nfs-qnap` StorageClass pointing at
   `192.168.178.254:/k8s`, mounting with `nfsvers=4.1` and
   `reclaimPolicy: Retain`.
4. Verify the node plugin and a test PVC:
   ```bash
   kubectl -n kube-system get pods -l app=csi-nfs-node
   ```

Do not make `nfs-qnap` the default StorageClass. Prometheus and Loki stay on
`local-path`: NFS is not supported for the Prometheus TSDB or Loki's filesystem
store.

## 7. Backups

Host-side backups run from Proxmox to `qnap-backups`
(`192.168.178.254:/k8s-backups`); details are in
[`proxmox-host.md`](proxmox-host.md) §7.

Done:

- nightly `vzdump` of VM 101 at `03:00`, snapshot mode, zstd, 7 daily / 4 weekly /
  2 monthly
- etcd snapshot at `02:30`, newest 30 kept

Remaining:

1. Restore test: `qmrestore` to a scratch VM ID, and an etcd snapshot restore.
2. HBS 3 offsite copy to Backblaze B2 or Cloudflare R2, with client-side
   encryption.
3. PVC backups (restic or K8up) once `nfs-qnap` is in place.

## 8. Adding capacity later

The old host is retired but intact. When you need more capacity:

1. Change its management IP so it no longer uses `192.168.178.249`.
2. Power it on and either:
   - add its VMs back as **workers** (re-image them; do not try to move a
     control-plane role in place), or
   - keep it as a separate lab host.
3. Restore workloads from Git and persistent data from the QNAP.

Do not create a two-node Proxmox cluster and do not run a two-member etcd. Both
need an odd number of members for fault tolerance: one node is fine, three is
HA, two is strictly worse than one.
